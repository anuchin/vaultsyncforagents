Two additional defects prevent reliable empty-folder synchronization in the daemon. Development dependencies also have outstanding security advisories.

Evidence scripts and outputs were created under the ignored `dist/` directory; this report is the only new review document.

## Source findings

### 1. P1 — Enumeration failures become deletion candidates

Locations: [Node storage enumeration](../packages/node-runtime/src/storage.ts#L157), [Obsidian file enumeration](../packages/plugin/src/adapters/obsidian-storage.ts#L278), [scan deletion inference](../packages/core/src/scan.ts#L358).

The Node adapter catches every `readdir` failure and returns an empty subtree. It also suppresses every file `stat` failure. The Obsidian adapter similarly suppresses listing and stat errors. Neither supplies an indication that the inventory is incomplete. The scanner treats tracked paths absent from that inventory as local deletions.

A fault-injection probe made `readdir` throw `EACCES` for one child directory while the vault root remained writable. The scan returned `/blocked/keep.md` as a deletion although the file still existed. Such a scan can advance to tombstone commits. The mass-delete guard only blocks when both more than 25 entries and more than 50% of tracked entries would be deleted; an unreadable small subtree bypasses it.

Fix: distinguish disappearance from permission/I/O failures, abort incomplete scans or explicitly protect inaccessible subtrees, and ensure neither file nor folder deletion inference uses an incomplete inventory. Add regressions for child-directory `EACCES`, file stat errors, and root unavailability. The root-unavailability probe demonstrates deletion inference only; inability to persist state can also stop a full cycle, so propagation depends on which part of the filesystem remains writable.

### 2. P1 — The daemon discards symlink deletion protection

Locations: [trash storage delegation](../packages/daemon/src/trash.ts#L166), [daemon storage construction](../packages/daemon/src/daemon.ts#L139), [scanner symlink protection](../packages/core/src/scan.ts#L285).

`NodeStorageAdapter.listSymlinks()` reports links so scans can protect indexed entries hidden beneath them. `TrashGuardStorage` wraps that adapter in every real daemon client but does not expose `listSymlinks`. The scanner therefore sees no links while `listFiles` still omits their contents.

Reproduced with a directory junction at `/notes`: scanning the raw adapter yielded zero deletions; scanning the same filesystem through the daemon wrapper yielded a deletion for `/notes/keep.md`. A small set of affected files bypasses the mass-delete guard and can be tombstoned on other devices.

Fix: delegate `listSymlinks` through the wrapper and test the complete daemon storage composition, rather than only the raw adapter's link policy.

### 3. P1 — Filesystem operations can escape the vault through links

Locations: [host path mapping and operations](../packages/node-runtime/src/storage.ts#L43), [atomic write parent creation](../packages/node-runtime/src/util.ts#L36).

Vault-path normalization prevents lexical traversal, but it does not check filesystem links in path components. Direct reads, writes, renames, and directory creation follow symlink/junction ancestors. Skipping links during enumeration does not protect incoming remote operations.

A real Windows junction pointed `<temporary vault>/notes` at a separate temporary directory. Calling `writeFile('/notes/remote.md', ...)` created the file in that outside directory. A paired client could trigger the same path through a remote create; this requires a pre-existing local link and authorized sync access, and is not an unauthenticated network exploit. The exposure is particularly significant for a daemon running as root.

Fix: enforce containment for operations against actual filesystem ancestry, reject links in every touched component, and validate both sides of renames. Include remote pull tests through a junction and consider races between checking ancestry and performing the operation.

### 4. P1 — Trash protection deletes after any read failure

Location: [trash read failure branch](../packages/daemon/src/trash.ts#L94).

`TrashGuardStorage.deleteFile` treats every exception from `readFile` as “already gone” and immediately calls the underlying delete. A read permission error or I/O fault can therefore remove existing bytes without creating the promised safety copy. Reading a file and deleting its directory entry require different permissions on Linux, so inability to read does not imply inability to delete.

A probe injected an `EACCES` read failure for an existing temporary file. The wrapper resolved successfully and the file was gone. This isolated reproduction establishes the wrapper defect; whether a full sync reaches it depends on earlier scan and divergence checks. For example, a fast scan may skip reading a file whose size and mtime still match the index.

Fix: suppress only a confirmed missing-file condition; propagate permission and I/O errors so the remote deletion retries without destroying the local file. Add a regression asserting that the original bytes survive a failed safety read.

### 5. P2 — Remote empty-folder deletions never remove daemon directories

Locations: [trash storage delegation](../packages/daemon/src/trash.ts#L166), [core directory removal](../packages/core/src/engine.ts#L290).

The same wrapper also omits the optional `removeDir` method, although the inner Node adapter implements it. Core deliberately falls back to recording the tombstone without removing the directory when that method is missing. Subsequent stale-directory cleanup still sees the same wrapper and cannot remove it.

Reproduced: `removeDirIfVacant` through the wrapper returned `false` and left the empty directory present. Metadata can converge while the VPS directory tree remains different from the other devices.

Fix: delegate `removeDir` and add a daemon integration test for remote folder tombstones and pruning an emptied parent after a file deletion.

### 6. P2 — Local empty-folder changes do not trigger daemon sync

Locations: [watcher subscriptions](../packages/daemon/src/watcher.ts#L88), [daemon client composition](../packages/daemon/src/daemon.ts#L130).

The watcher subscribes only to file `add`, `change`, and `unlink` events. It intentionally ignores `addDir` and `unlinkDir`, assuming file events will trigger a scan. That assumption fails for creating or deleting an empty directory. The daemon's periodic ticker writes health snapshots; it does not trigger reconciliation.

Reproduced with the real watcher: after settling initial events, creating an empty directory yielded no callback events. With a quiet connection and no other file changes, the folder remains unsynchronized until another reconciliation trigger or reconnect.

Fix: translate relevant directory events into scan triggers and test creation and removal of empty folders without an accompanying file edit. A periodic reconciliation fallback can also address missed watcher events.

## Dependency and verification results

`npm run typecheck` passed for all workspaces. `npm test` exited successfully after running all seven suites: core, node runtime, CLI, Worker, daemon, dashboard, and plugin. The daemon, dashboard, and plugin suites were also run separately and passed. The passing baseline does not cover the reproduced adapter-composition and failure-path defects above.

Worker tests emitted Durable Object invalidation diagnostics during the run but completed successfully. The installed local runtime also reported that the configured `2026-08-01` compatibility date exceeded its supported `2026-03-10` date and fell back. Consequently, local test success does not establish exact behavior under the intended deployed compatibility date.

`npm audit --omit=dev --json` reported zero production dependency vulnerabilities. The full audit reported 15 affected package entries: 2 critical, 8 high, 4 moderate, and 1 low. These are package-level counts, including inherited dependency alerts, not 15 independent demonstrated exploits in this application.

The critical entries are `tinypool` and its parent `vitest`. The reviewed [Tinypool run-options advisory](https://github.com/advisories/GHSA-85c8-ppgw-ccpr) requires prototype pollution plus a particular options-object execution path; the related [worker-options advisory](https://github.com/advisories/GHSA-5gmw-xhrv-c9v3) describes another inherited-options path. This audit did not establish either exploit in the deployed sync service. Development-tool updates still deserve a separate change followed by all compatibility and test checks. Other flagged tooling includes Wrangler, Miniflare, esbuild, and transitive networking packages. No dependency versions or lockfiles were changed.

## Implications for eventual three-device sync

This project has the intended architecture: a user-owned Cloudflare Worker provides the sync authority and R2 content storage, Obsidian plugins serve the PC and phone, and a watched daemon serves the VPS. The VPS is a client, rather than the sync server.

Windows service installation is explicitly deferred in this version. Using the desktop plugin therefore synchronizes while Obsidian is running; syncing edits while it is closed requires a separately managed daemon or scheduled/background process, with one client owning the vault at a time. Mobile live sync is available while Obsidian is foregrounded and catches up on open; it does not promise continuous background execution.

The design uses HTTPS/WSS and device authentication but does not provide end-to-end encryption. The vault documentation identifies an API-token note, and ordinary note paths are included by the default ignore rules; moving to this system therefore also moves such content into the user's Cloudflare storage unless exclusions are deliberately configured.

Before a future activation, address the four P1 findings, correct daemon folder handling, choose the intended Worker and vault locations, preserve separate recovery copies, and verify new edits in each direction plus a disconnect/reconnect. The present 392-file match means there is no demonstrated content divergence to repair in the compared scope. No activation was performed during this audit.
